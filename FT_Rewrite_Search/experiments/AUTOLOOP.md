# 24 小时自动实验循环（2026-10-29 起）

执行者：Claude 会话「Fir 实验进程」。用户通过 Remote Control 随时查看或叫停。

## 1. 循环怎么转

每一轮按下面 6 步走：

1. **收结果**：查 Fir（`squeue`/`sacct`）和本地后台任务，拉回已结束作业的输出（`fir-pull`，大文件留在 Fir 上就地分析）。
2. **判定**：按 §3 队列里每项的通过标准判定，写明"通过 / 不通过 / 需要人判断"。
3. **记录**：在 `experiments/LOG.md` 追加一节（日期、作业号、用时、结果、与标准对比、原因）；Fir 作业同时记 `Fir/LOG.md`。
4. **更新队列**：改本文件 §3 的状态列；不通过时按"失败处理"列加修复项。
5. **启动下一项**：依赖满足的项按 §2 的规模规则放到本地或 Fir。
6. **等待**：每个 Fir 作业配一个后台轮询（每 5 分钟 `squeue`，作业结束才唤醒我，等待期间不耗 token）；另设 30–60 分钟的保底唤醒，防止轮询本身挂掉。

## 2. 规则和上限

- **在哪跑**：几分钟、几 GB 以内的单进程在本地跑；其余交 Fir；拿不准就交 Fir。CPU 作业用 `def-ffang26_cpu`；需要 GPU（例如大规模采样）时可以用 `def-ffang26_gpu`（用户 2026-10-29 同意）。
- **Fir 资源**（用户 2026-10-29：资源充足，内存可以申请高一点）：内存按需申请，默认 32G，不确定就给 64G；同时最多 3 个作业（array 算 1 个）；单个作业时限 ≤ 24 小时。不设 CPU 小时上限，但不做没有明确目的的大规模扫参。
- **改代码**：改 `ftrs/` 之后，提交 Fir 之前必须先在本地跑过 `test_generalize.py`、`e1_5_negative_control.py`、`test_appc.py`，输出与参考（`results/regress_ref/`）一致才提交。
- **不做的事**：不改任何通过标准；不 git commit / push；不改其他会话正在用的文件；不下载未经同意的文件；Fir 登录节点上只做提交、查询和几秒的小命令。
- **通知用户**（手机推送）：阶段性结论（某项通过或不通过）、需要研究判断、ssh 连接断开（要批准 Duo）、触发停止条件。其余只写 LOG。

- **记录**（用户 2026-10-29）：每个运行一结束就把结果写进 `experiments/LOG.md`，Fir 作业同时写进 `Research/Fir/LOG.md`；失败、取消、作废的也记，写明原因。
- **轮次报告**（用户 2026-10-29）：每轮给用户的报告也追加到 `experiments/LOG.md`（标题“AUTOLOOP 轮次报告”）。
- **唤醒频率**（用户 2026-10-29）：注意 token 消耗，保底唤醒固定 30 分钟；每轮只做必要的读取和输出。
- **自主决定**（用户 2026-10-29）：队列之后的实验由我根据已有数据和结论自行决定，每个新实验在 §3 加一行（目的、依据、通过标准），照常记录；需要改变论文主线或修改通过标准时仍先问用户。
